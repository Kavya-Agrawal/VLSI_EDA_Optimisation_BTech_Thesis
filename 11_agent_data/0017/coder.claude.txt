The fanout-tree move is written, but I haven't built or run it, so it is untested. The task rules said to leave building and testing to you. I also couldn't check that it compiles.

The move fires on every driver with fanout ≥ 40, not only in the recovery phase. `SetupLegacyPolicy.cc` isn't on the editable list, so I couldn't hook the recovery phase directly. Stock SplitLoad uses the same generator in the main repair loop, so the stock trajectory is no longer byte-identical on those nets. The recovery phase's WNS-floor/TNS check journals and rolls back a bad tree. In the main loop only the usual per-pass "better" check protects against one.

- **What it does:** for each qualifying driver, the generator sorts sinks by slack and keeps the most critical ones on the driver. It splits the rest into 1–4 groups, each behind its own buffer placed at the group centroid. Each buffer is chosen from all non-dont-use buffer masters.
- **How the variant is picked:** it scores 16 variants with a lumped delay model and takes the best. The model predicts the worst slack from the driver's drive resistance and the buffer cell data. If no variant is predicted to gain at least 1 ps, it falls back to the stock half-split.
- **Selection is analytic only:** I did not implement the "several trees judged on measured STA inside a journal" part. Nested journals looked unsafe, and the model ignores wire RC and slew, so some trees may be worse than predicted.
- **Journaling:** the move is an ordinary split-load move, so it goes through the existing commit and rollback path.
- **Determinism:** buffers are sorted by name and sinks by slack, with the existing name tie-break. There is no randomness.
- **Counters:** `~SplitLoadGenerator` prints the four `RSZ_EVOLVE` lines and then clears them. If the policy builds several generators in one call, you'll see one set of lines per generator. A sum over the lines is the right total.
  - `fanout_tree_built`
  - `fanout_tree_buffers`
  - `fanout_tree_sinks_isolated`
  - `fanout_tree_stock_fallback`
